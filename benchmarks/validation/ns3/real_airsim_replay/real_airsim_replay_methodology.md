# Paired ns-3.49 / R1 experiments

## Scope

This package runs two controlled replay cases over common mobility and packet schedules:

- **C — AirSim replay:** the protected three-UAV CSV (`airsim_real_3uav_120s.csv`), 600 frames, and the original 5 Hz aggregate traffic schedule. The replay clock is `monotonic_time_s` relative to the first sample. The measured wall/monotonic span is 119.7909209 s; the AirSim simulation-clock span is 118.283523328 s (difference 1.507397572 s). Simulation timestamps are provenance, not the replay clock.
- **D — R1 synthetic mobility:** 20 UAVs, 30 one-second frames, 120 m × 120 m horizontal area, 5–50 m altitude, 1.0–2.4 m/s sampled horizontal speed, and independently sampled vertical velocity in [-0.5, 0.5] m/s. The trace is generated by the unchanged R1 `SyntheticMobility` implementation, which advances heading/velocity and reflects at boundaries; it is not RandomWaypoint mobility.

The original AirSim CSV is checked against SHA-256 `9C09B80E19CC6321BA61899565D34CA96EA4D0C02C3B0E0E4F969DD7F93115E3`. Its bytes are not transformed or overwritten. Normalized inputs are separate files. The NED z-coordinate is negated only for ns-3's Cartesian coordinate convention; distances are invariant. Python R1 consumes the original common-NED coordinates.

## Paired repetitions and traffic

Each condition uses 30 repetition labels (`20261029`–`20261058`) and its matching traffic seed (`20380942`–`20380971`). The same generated packet IDs, source/destination pairs, generation times, and mobility evaluation frames are replayed in ns-3 and Python, and across AODV and OLSR. ns-3 uses fixed base seed `20261029` with run numbers 1–30, paired by repetition. The 30 replays are RNG/traffic replications, not 30 AirSim flights.

- C: 599 scheduled UDP packets per repetition over the measured AirSim trace.
- D: 150 scheduled UDP packets per repetition over 30 s (5 packets/s total).
- UDP application payload: 256 bytes including the 12-byte experiment packet-identity header.
- ns-3 routing warm-up: 5 s; drain after the final scheduled event: 10 s.
- Position snapshots are applied at exact packet evaluation frames. No interpolation or continuous movement between samples is claimed.

## Network models

ns-3 uses the standard ns-3.49 AODV and OLSR modules, ad-hoc 802.11g on channel 1 / 20 MHz, 16 dBm transmit power, fixed 6 Mbps data/control rate, -101 dBm receive sensitivity, and MAC retry limit 7. The principal comparison channel is a 35 m `RangePropagationLossModel` hard cutoff. These settings are executable and recorded, but they are **not calibrated** to AirSim, a specific radio, or a measured link budget.

Python uses the existing R1 `AODV-like reactive` and `OLSR-like proactive` abstractions with the same binary 35 m graph and packet schedule. These abstractions are not the standard ns-3 protocol implementations. The two simulators also have different channel, MAC, packet, and routing execution semantics; equal inputs do not establish physical/model equivalence.

## Metrics and accounting

- PDR denominator: application packets generated from the schedule. The event audit retains scheduled, generated, socket-accepted, received, and undelivered distinctions.
- ns-3 delay: application send to first receive of the same packet ID; also retains FlowMonitor IP delay. A UDP `SendTo` rejected by the local stack is not silently discarded: it is recorded as `socket_send_rejected;cause_unattributed`. Accepted but not received by the end of drain is separately recorded. FlowMonitor loss is reported independently.
- FlowMonitor IP Tx/Rx/loss counts are diagnostics separate from application packet-identity counts. The ns-3.49 documentation defines `lostPackets` as packets assumed lost when not reported for 10 seconds; packets still queued below IP at simulation end may be counted as lost and may also count toward received or dropped packets. Therefore, `lostPackets` is not guaranteed to equal `max(Tx - Rx, 0)` or application packets undelivered after drain. In this experiment it exceeded `max(Tx - Rx, 0)` in all 30 D/AODV runs. Application unique-delivery counts define PDR, and application packets undelivered after drain define application non-delivery. See the [official ns-3.49 FlowMonitor documentation](https://www.nsnam.org/docs/release/3.49/models/html/flow-monitor.html).
- Python delay is model-based: R1's analytical base, per-hop, discovery/control penalties, and seeded jitter. It is not packet-level latency and must not be interpreted as a radio-measured comparison with ns-3.
- Python hop count uses the selected R1 route. ns-3 `forwarding_based_hops_estimate` is derived from FlowMonitor forwarding counters and is not an exact per-packet hop count.
- Python model-control packet totals sum the R1 `decision.control_packets` counter; they are abstract events, not serialized messages or byte counts. ns-3 control-message/byte totals remain `NA`; this driver does not instrument routing control traffic. Python route-event counters are abstraction-specific and are not directly equivalent to ns-3 control packets.
- Paired differences are computed by repetition seed. Reported 95% confidence intervals use a two-sided Student-t critical value and expose the half-width. A missing latency observation remains `NA`; no success-shaped fallback is used.

## Topology interpretation

Independent distance/graph calculations use the same 35 m cutoff on every source mobility frame and every scheduled traffic pair. C is expected to be fully connected in all 600 frames. That confirms input/mobility and direct-link replay only; it is not a dynamic multi-hop routing stress test. D may contain disconnected pairs and multi-hop paths; its topology counts are exported separately.

## Reproducibility

`run_ns3_paired_experiments.py` builds the C++ driver with at most two compile jobs, runs a C/D first-seed pilot and byte-identical deterministic repeat, then completes the remaining paired seed runs. It writes the settings, run log, trial-level CSV, per-packet audit, topology validation, summary, paired statistics, and validation JSON. The PowerShell plotting helper converts trial summaries into the PNG comparison figure. Input hashes and the ns-3 source commit (when available) are recorded in the settings and validation manifests.

The pilot can be reproduced with `--pilot-only`; the full study omits that flag. Supply explicit paths using the WSL Linux filesystem for ns-3 and R1 source files.
